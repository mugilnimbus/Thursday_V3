# Contracts and Integrations

Shapes and field lists are the agreed contract; the exact schemas are in the `contracts` package, guarded by snapshot tests. Flows are in [FLOWS.md](FLOWS.md).

## Boundary overview

| Boundary | Contract | Style | Auth | Timeout, retry, idempotency |
|---|---|---|---|---|
| Client to gateway | REST `/v1` plus one WebSocket | sync plus server push | Device token (bearer); the PC dashboard uses the trusted localhost listener | Clients reconnect with backoff; sends carry `client_message_id`; creates take `Idempotency-Key` |
| Gateway to voice agent | Internal chat API (streaming) | sync stream | Service token | Message queues at the gateway if the voice agent is down |
| Voice agent to main agent | A2A 1.0 `SendMessage` with `returnImmediately` and a push webhook | async | Service token | Push retried a few times; reconcile with `GetTask` and `ListTasks` after restart |
| Gateway to main agent | A2A (`CancelTask`, approval answers), task-control extension, Management API | sync | Service token | Short timeout; safe to repeat |
| Agents to gateway | Event ingest `POST /v1/events` (batched) | async | Service token | At-least-once from the outbox, deduplicated by `event_id` |
| Gateway to speech service | `POST /v1/transcribe`, `POST /v1/decode`, `POST /v1/speak`, `GET /v1/voices`, `POST /v1/warm` | sync | Service token | Long timeout for the first use (models load or download); a failure is `503` to the client, typing still works |
| Gateway to each agent (retention) | `PUT /v1/retention` (`RetentionSetting`) | sync | Service token | Repeated once a minute until the agent confirms the period; safe to repeat |
| Collector and services | `GET /metrics` (JSON map) scrape, then `POST /v1/metrics` (`MetricsSample`) to the gateway | async | Local only; push needs the service token | Missed scrapes are gaps |
| Main agent to tool server | MCP over stdio, including the input-required retry; the chat id travels as call metadata; one-off clean-up commands of the same program | sync | Process boundary | Tool timeout, MCP cancellation |
| Agents to LLM endpoint | OpenAI-compatible `/v1/responses`; LM Studio native API for model lifecycle; the built-in llama.cpp is a child process spoken to over `/v1/chat/completions` on localhost | sync stream | API key from the credential store; a random per-run key for the built-in llama.cpp | Three retries with increasing delay |

Versioning: REST prefix `/v1`, `schema_version` on every event, A2A 1.0, a versioned extension URI, MCP version negotiation. Only the gateway is reachable from the tailnet; all other services bind to localhost.

## A2A usage

- The main agent is an A2A server with an Agent Card; the voice agent and the gateway are A2A clients.
- Each new instruction is a new task in the chat's `contextId`. Finished tasks cannot accept further messages (the protocol returns an unsupported-operation error), so amending a running task means stopping it and sending a new task.
- The voice agent sends with `returnImmediately` and a task push-notification config. The main agent pushes on terminal states and on `INPUT_REQUIRED` and `AUTH_REQUIRED`. Push payloads carry a short summary message; full output travels as artifacts and is fetched with `GetTask`.
- Approval answers continue an `INPUT_REQUIRED` task with a message carrying the same `taskId` and `contextId` and a data part `{approval_id, decision: allow_once | allow_always | deny}`.
- **Task-control extension** (versioned URI, placeholder): declared in the Agent Card, activated with the `A2A-Extensions` header. Adds `PauseTask` and `ResumeTask` (both repeatable; errors on finished tasks). The task stays `WORKING` with a metadata flag `none | pausing | paused`. Stop is the standard `CancelTask`.

Details of this contract:

- Transport is JSON-RPC at `POST /a2a` on the main agent, with `Authorization: Bearer <service token>` and `A2A-Version: 1.0` (a missing version header is treated as 0.3 and refused).
- A new task's message carries `contextId` = chat id and metadata `thursday.project_id` and `thursday.project_folder` (an existing absolute folder). The voice agent's code sets these from the gateway request; the model never does. It also names the request, in metadata `thursday.request` (and uses the same value as the message's `messageId`): the name is worked out from the chat, the user's message, and the task's position among the tasks that message starts, so it is the same every time the request is sent. The main agent starts one task per name. A request that arrives again under a known name (its first answer was lost on the way) is answered with the task it already started, in the shape of a first answer, and nothing new runs. The push token of a named request is worked out from the name as well, because the main agent keeps the token it was given first. A new task in a chat the main agent was told to delete is refused (`-32004`, "this chat was deleted").
- The approval request is a data part `{kind: "thursday.approval_request", approval_id, task_id, chat_id, tool, summary, arguments, expires_at}` on the `INPUT_REQUIRED` status message. The answer is a data part `{kind: "thursday.approval_answer", approval_id, decision}`, with optional metadata `thursday.answered_by`.
- JSON-RPC errors: `-32041` approval already resolved, `-32040` task not pausable (extension), `-32004` a text message to a running task, `-32602` missing project metadata or a forbidden part, `-32601` extension not activated, `-32001` task or approval not found.
- Pushes go only to the voice agent's `POST /v1/push`, checked with the per-task `X-A2A-Notification-Token` that the voice agent chose.

## Gateway to voice agent (internal chat API)

- `POST /v1/chats/{chat_id}/turns` with the service token and `{client_message_id, text, project_id, project_folder}`. The reply streams as NDJSON lines: `{"type": "delta", "text"}`, then `{"type": "done", "text"}`, or `{"type": "error", "message"}`.
- Idempotent on `client_message_id`: a repeated turn returns the stored reply without calling the model.
- `POST /v1/chats/{chat_id}/direct` with the same body starts a task from the user's words, unchanged, without the voice model. It returns `{"task_id"}` (or `{"replayed": true}` for a repeat, or `{"answered": text}` when the words were a plain yes or no to a waiting approval). `503` when the main agent cannot be reached (the gateway keeps the message queued and retries, and the retry starts no second task: see the request name above); `409` when the main agent refuses the task (the message fails with the reason); `410` when the chat was deleted (the message fails). A turn (`/turns`) answers `410` for a deleted chat too. The `user_message` event carries `direct: true` and the `delegation` event `by: "direct"`. When the task finishes, the voice agent writes the report itself (see `docs/FLOWS.md`).
- `503` when the voice model endpoint is unreachable, so the gateway keeps the message queued and retries.
- `POST /v1/hear` with a WAV clip as the body: the voice model itself writes down what is said and the reply is `{text, audio_seconds, seconds, by: "voice_model"}`. `409` means "use speech-to-text instead": the model cannot hear, the clip is longer than 30 seconds, nothing was heard, or the words are more than fit in the clip. `422` when the body is not WAV. The model is loaded if it was not.
- `DELETE /v1/chats/{chat_id}` (delete saga participant, repeatable). Besides removing what it holds, each agent notes that the chat was deleted and keeps the note for a week: no turn or task starts in that chat afterwards, and work that was still under way (a reply being written, a task's report, a task winding down) writes and sends nothing more for it. Replay (`GET /v1/replay?after=`) and prompts (`GET`/`PUT /v1/prompt`) use the service token.
- `GET`/`PUT /v1/retention` with `{days}` (0 to 3650; 0 keeps working data until it is deleted): how long this agent keeps its working data. The main agent serves the same pair. Each agent stores the period itself and answers with the period now in force.
- Spoken approvals are recognised by code only while an approval is pending and only for a whole-message phrase (for example "yes", "allow always", "no"); the voice model has no approval tool.

## Event envelope

Every service sends events to the gateway in this shape:

- `event_id` (unique, used for deduplication) and `schema_version`
- `source` (`voice`, `main`, `collector`, `tool`), `seq` (per-source counter for ordering and gap detection), `ts`
- `project_id`, `chat_id`, optional `task_id` (project and chat are absent only for global events such as a model load)
- `type`: user message, assistant message (voice agent replies, including spoken task updates), delegation, LLM call, tool call, approval requested, approval resolved, task state, compaction, model load, notification, error
- `payload`: JSON specific to the type

Delivery is at-least-once with per-source ordering. Any text in a payload longer than 20,000 characters is cut and marked with how much was removed, so large bodies (LLM requests and responses, tool output) are capped part by part. Bodies are stored; headers are never stored.

Some payloads carry optional fields clients may use: `task_state.queued` (true while a task waits for its turn on the model), `llm_call.error` (why a model call failed), and `compaction.harder` and `compaction.from_digest` (the window was compacted harder after an overflow; the summary was built without the model).

Tool-call events carry a `status`: `requested` (the model asked for it), `running` (the executing call starts after approval), then `ok`, `error`, or `unknown` (the call started before a restart and its result was lost). Each agent serves its own events for rebuilds at `GET /v1/replay?after=<seq>` (service token).

## Client REST and WebSocket

All under `/v1` with `Authorization: Bearer <device token>`, except pairing claim.

| Group | Operations |
|---|---|
| Projects | List, create; read, rename, change folder, delete (gateway checks the folder exists) |
| Chats | List and create per project; read, rename, delete; page through messages; search across chats |
| Sending | `POST` a message with `client_message_id`; returns `202 {status, new, direct}` (delivered or queued); the reply arrives on the WebSocket. Sending a message that failed again, with the same id, queues it again. A chat holds at most 100 waiting messages: a new one beyond that is refused with `429` (code `rate_limited`, title "Too many waiting messages") and `Retry-After: 30`; a message that is already waiting is never refused again. Whether it goes through the voice agent or straight to the main agent is decided by the chat's switch when the gateway accepts it |
| Direct switch | `PATCH /v1/chats/{id}` with `{title?, direct?}` returns `{chat_id, title, direct}` and tells every client the chat list changed. Chat lists carry `direct`; so do the messages and pending messages of a chat, and the `outgoing` stream messages |
| Tasks and trace | Timeline after an event number; task with its trace (LLM request and response logs, tool call logs); pause, resume, stop |
| Approvals | List pending; answer with `allow_once`, `allow_always`, or `deny` |
| Tools | Tool server status per project; list and revoke a chat's allow-always rules |
| Monitor | `GET /v1/monitor?range=15m|1h|24h|7d` (latest and history); live values on `/v1/metrics/stream`, opened only while Monitor is visible. A sample's `storage` lists `{name, bytes}` for each service's databases and for the log files; it is measured about once a minute and is empty in the samples between |
| Agent settings | Per agent (`main`, `voice`): read and change the provider, endpoint, model, load and answer settings, and context limit; list the provider's models; load, unload, reload; store or remove the API key (write only). Details below |
| Other settings | System prompt read and write with versions; keep-awake and retention (`GET`/`PUT /v1/settings/general`: `keep_awake_paused_minutes`, `data_retention_days` from 0 to 3650 where 0 keeps working data until it is deleted, `metrics_retention_days` from 1 to 365; the earlier name `trace_retention_days` is still accepted and still answered); backup now and backup schedule (`POST /v1/backup`, `GET`/`PUT /v1/settings/backup`) |
| Devices | Create a pairing code (localhost listener only); claim a code; list and revoke devices (details below) |

**WebSocket** (`/v1/stream?after=<n>`, optional `chat_id`), server to client only; actions use REST. Message kinds: `catalog_changed` (a project or chat was created, renamed, or deleted; clients reload their lists), `chat_delta`, `timeline_event`, `task_state`, `approval_requested`, `approval_resolved`, `notification`, `metrics`, `status_banner`, plus `outgoing` (queued, delivered, or failed state of a sent message). Messages from stored events carry `pos`, the gateway's event position; on reconnect the client passes the last `pos` seen and the gateway replays what was missed. A client that falls too far behind is disconnected (close code 1013) and reconnects with its cursor. `GET /v1/status` includes `stream_pos`, the newest position, so a client that loads its screens over REST can join the stream from there.

Messages returned by `GET /v1/chats/{id}/messages` carry `pos`, the position of the event that stored them, so a client can merge stored and live messages without showing one twice.

**Agent settings.** The gateway forwards these to the agent that owns them (`{agent}` is `main` or `voice`) and stores nothing itself.

| Call | Body and result |
|---|---|
| `GET /v1/agents/{agent}/llm` | The effective settings: `provider` (`lmstudio`, `llamacpp`, `openai_compatible`), `base_url`, `model`, `load` (`context_length`, `eval_batch_size`, `flash_attention`, `offload_kv_cache_to_gpu`, `num_experts`, `moe_cpu_layers`, `gpu_layers`, `gpu_split`, `gpu_priority`), `inference` (`temperature`, `top_p`, `max_output_tokens`, `reasoning`), `llamacpp` (`installed`, `models_dir`, `gpu`, `devices` as `{index, name, total_mb}` once llama.cpp has been asked, `placement` in words for a model loaded with a fill order), `compact_at_tokens`, `idle_unload_minutes`, `idle_seconds` (since the loaded model was last used), `remembered` (the model and address each other provider used last), `api_key_set`, `sends_data_off_pc`, `supports_lifecycle`, `hears_audio`, `loaded` (`context_length`, `adopted`, `load_seconds`, or null), `reachable`. A null setting means the engine's default |
| `PUT /v1/agents/{agent}/llm` | Only the fields to change; a field sent as `null` returns to its `.env` value. `load` and `inference` are merged field by field. Also `models_dir`, `gpu`, `compact_at_tokens` (1024 to 2,000,000), `idle_unload_minutes` (0 to 1440; 0 never unloads). `load.gpu_layers` is `all` or a number; `load.gpu_split` is proportions like `3,1`; `load.gpu_priority` is the card to fill first (`0`, or an order like `1,0`) and takes the place of `gpu_split`. Changing `provider` puts away the model and address in use and brings back the ones that provider used last (or none), unless the same request sets them: a model name from one provider is never carried to another. `base_url`, when sent, must start with `http://` or `https://`; the built-in llama.cpp has no address, so a switch to it sends none (the clients leave an emptied address out). A body the agent cannot accept is answered `422` with `detail` reading "field: what is wrong" for each field. Returns the new settings. Changing a setting never loads a model. While the agent's model is in use (answering, or being loaded), the change is refused with `409` and the reason, and nothing is saved: applying it would close the provider under the call. The same goes for a new key, and for `unload` and `reload` |
| `GET /v1/agents/{agent}/models` | `{models: [{key, loaded, max_context_length, trained_for_tool_use, size_bytes, projector}], error}` for the saved provider. A problem (folder not set, endpoint down) comes back in `error` with an empty list, not as an HTTP error. Listing never loads anything |
| `POST /v1/agents/{agent}/model/{load, unload, reload}` | Loads with the saved load settings, frees the model, or does both. `reload` may carry load settings to save first. Long timeout: a load can take minutes |
| `PUT /v1/agents/{agent}/llm/key` | `{key}` stores the key for the agent's saved provider in the credential store; an empty `key` removes it. Returns the settings (with `api_key_set`), never the key. `api_key_held_back` is true when a key is stored for another address than the one in use: it is not sent until it is typed again. `503` when the system has no credential store |

`reasoning` is `default`, or `off` / `on` for the built-in llama.cpp, or an effort (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`) for a Responses endpoint; which efforts a model accepts is the endpoint's decision.

**Folders and files (read-only).** `GET /v1/fs/folders?path=` lists the sub-folders of an absolute folder on the PC (names only; an empty path lists the drives; folders the operating system hides are left out, which on Windows means the hidden mark and not a leading dot) and returns `model_folders`, the places where LM Studio keeps its models if they exist, so a client can pick a project folder. `GET /v1/projects/{id}/files?path=` lists a folder inside the project, and with `q=` searches file and folder names in the whole project (dependency and build folders skipped; at most 200 results). `GET /v1/projects/{id}/file?path=` returns `{text, size, truncated, binary}` for the first 200 kB of a text file. Project paths are resolved, including links, and anything outside the project folder is refused with `422`.

**Deleting.** Deleting a chat or project removes every record of it from every service; only the folder on disk is left alone. The gateway first stops the chat's running tasks, then asks the main agent (`DELETE /v1/chats/{id}`, and `DELETE /v1/projects/{id}` for a project) and the voice agent (`DELETE /v1/chats/{id}`) to delete, repeating until each confirms, then purges its own rows. The main agent removes tasks, approvals, allow-always rules, call marks, transcript, chat summary, LangGraph checkpoints, A2A task and push records, the chat's events in its outbox, and the chat's rows in the project's tool call log; for a project it also stops the tool server and removes the project's tool call log. The voice agent removes transcript, task records, turn records, and the chat's outbox events. The gateway refuses events that arrive later for a deleted chat or project (they are acknowledged so the sender moves on, and not stored), and at start removes rows whose chat or project no longer exists.

**Pairing.** `POST /v1/devices/pairing` (localhost listener only) returns `{code, expires_at, address, pairing_uri}`: an 8-character code shown as `ABCD-EFGH` (no 0/O or 1/I), valid once for five minutes; a new code replaces the previous one. `address` is this PC's tailnet HTTPS URL (`GATEWAY_PUBLIC_URL`, else read from `tailscale status`); `pairing_uri` is `thursday://pair?url=<address>&code=<code>`, the text a QR code will carry. `POST /v1/devices/claim {code, name}` needs no token and returns `201 {device_id, token}`; the token is shown once and only its SHA-256 hash is stored. A wrong or expired code is `422`; after 5 failed claims in a minute every claim is `429 rate_limited` with `Retry-After: 60`, and 10 failures burn the current code. `GET /v1/devices` lists `{device_id, name, created_at, last_seen}`; `DELETE /v1/devices/{id}` revokes at once: the token stops working and the device's open WebSockets close with code 1008.

**Speech.** `GET /v1/speech` returns `{available, voices}`. `POST /v1/speech/transcribe` takes the recorded audio as the request body (webm, m4a, or wav; at most 15 MB) and returns `{text, audio_seconds, seconds, by}` (and `language` from Whisper). The gateway first has the speech service decode the recording to WAV (`POST /v1/decode`) and asks the voice agent to hear it (`by: voice_model`); if the model cannot, or anything in that path fails, the speech service's Whisper transcribes it (`by: whisper`). `POST /v1/speech/speak {text, voice?}` returns WAV audio (24 kHz, 16-bit, mono); markdown marks are removed and long text is cut at a sentence near 2000 characters. The gateway forwards these to the local speech service with the service token and stores no audio. The client sends the transcribed text as a normal chat message, so delegation, spoken yes/no approvals, and the timeline are unchanged. `503` when the speech service is not running or a model cannot load; `422` for an empty recording or an unknown voice. A client reads a reply aloud one piece (a clause or a sentence) per `speak` call. `POST /v1/speech/warm {speak?, listen?}` answers `202` at once and starts loading, in the background, what the coming turn will need. With `listen` true (the default: the microphone was pressed) that is the voice agent's model, the text-to-speech engine when `speak` is true, and the speech-to-text engine unless the voice model can hear. With `listen` false (a typed message whose reply will be read aloud) it is the text-to-speech engine alone. It is safe to call on every press and every send; a failure only means the turn loads things itself.

Event ingest (`POST /v1/events`, service token) is served only on the localhost listener.

**Errors** use `application/problem+json` with a stable `code`: `401` unauthenticated, `404`, `409` (approval already resolved, task not pausable), `422` invalid input, `429` rate limited (pairing claims), `503` with the reason when a dependency is down.

## MCP contract (main agent and tool server)

- The LLM never calls the tool server. It names a tool and arguments; the main agent (MCP client) sends `tools/call` and returns the result to the model.
- When a tool needs approval the server returns an input-required result containing an elicitation request (a yes or no form) and a `requestState`. The client asks the user and retries the same call with the answer and `requestState`. The user's answer is `accept`, `decline`, or `cancel`; a 300 second timeout is reported as `cancel` ("user did not respond"), a refusal as `decline`.
- The project folder is passed to the server as its root (MCP roots).
- Some shell commands are never run: the tool server answers them with a tool error and no approval request (erasing disks, deleting outside the project folder, changing the PC's security settings, sending, publishing or fetching files over the network, and commands whose text is hidden).
- MCP has no session concept: the shell session tool returns an explicit session handle and takes it on later calls. Handles are lost if the server process stops, so the main agent does not stop a server with an open session.
- Tool results with `isError` go to the model so it can correct itself.
- **The chat a call belongs to** is sent beside the arguments, in the call's `_meta` under `app.thursday/chat_id`. The main agent's code sets it; the model never sees it and a tool never acts on it. The tool server records it in its call log only when it has the shape of an id (letters, digits, `_` and `-`, at most 64), so that deleting the chat can remove its calls.
- **Clean-up commands.** The tool server program also runs one-off commands against its own log files and prints one JSON line: `forget-chat --chat-id <id>` (`{removed}`) and `forget-project --project-id <id>` (`{files}`). The main agent runs these when a chat or project is deleted; another service never opens the tool server's files. The server is started with `--keep-days <n>` (0 keeps the log until it is deleted) and prunes its own log when it opens and once an hour.
- The server enforces the workspace sandbox and the permission policy itself; nothing in a prompt can widen them. Allow-always rules are kept by the main agent, keyed by chat, and answer repeat requests.

## LLM endpoint contract

- Chat uses `/v1/responses` with streaming for LM Studio and OpenAI-compatible endpoints, and `/v1/chat/completions` with streaming for the built-in llama.cpp (its native API; its `/v1/responses` only converts to it). The harness keeps its own transcript; every call sends its full input. Chaining with `previous_response_id` is supported by the LLM package but not used today.
- Token counts come from standard usage (input, output, cached, and reasoning tokens). Time to first token and tokens per second are measured by the harness from its own stream timing, so they work for every provider. The rate runs from the first piece of the reply in which the model produces anything, thinking included, to the end: the count of output tokens includes thinking, so counting from the first words of the answer would make a reply that was mostly thinking read several times too fast. Time to first token is the wait for the first piece with something in it; on the built-in llama.cpp, whose thinking does not reach the client library, that is the first text or tool call. Context window comes from the LM Studio provider and shows as unknown otherwise.
- **Provider interface** (list models, ensure loaded, unload, reload, reachable), with three providers:
  - LM Studio: chat, list models, load with `context_length`, `flash_attention`, `offload_kv_cache_to_gpu`, `eval_batch_size`, `num_experts`, unload, loaded context length.
  - Built-in llama.cpp: starts `llama-server` with `-m <file>`, `-ngl 99`, `-c <context, 8192 by default>`, `--host 127.0.0.1`, `--port <free port>`, `--api-key <random>`, `--jinja`, `--mmproj <projector>` when one sits beside the model, and from the load settings `-fa on|off`, `--no-kv-offload`, `-b` and `-ub`, `--n-cpu-moe`; a chosen GPU is passed as `CUDA_VISIBLE_DEVICES`. It waits for `/health`, then reads the context length and what the model accepts (`modalities`) from `/props`. A model key is a path inside the models folder; anything that resolves outside it is refused.
  - Generic OpenAI-compatible: chat and `/v1/models` only.
- **Answer settings** are sent only when set: `temperature`, `top_p`, an output token limit, and for Responses endpoints `reasoning: {effort}`. For llama.cpp, thinking is switched with `chat_template_kwargs: {enable_thinking}`.
- Model loading is explicit (adopt a loaded model or load with configured parameters). JIT loading is not relied on. Nothing is loaded when a service starts.
- Request bodies are kept for traces as sent. A response is kept as the response it carried: for a Responses stream the final event's response without the fields the request already holds (`tools`, `instructions`, `input`); for chat-completion chunks one assembled message with its usage; for a stream that ended early what arrived, marked `incomplete`. `Authorization` and other headers never are kept.

## External integrations: findings and mismatches

| System | What holds | Mismatch or unknown | Handling |
|---|---|---|---|
| LM Studio REST and OpenAI-compatible API | `/v1/responses` stateful and streaming with standard Responses events; `POST /api/v1/models/load` applies the load parameters above; `GET /api/v1/models` returns `max_context_length` and each loaded instance's config; reasoning arrives as standard `reasoning` output items; usage includes cached and reasoning tokens | No speed stats in `/v1/responses` (only the native chat API has them); loading an already-loaded model creates a second instance; JIT loading is on by default and loads unloaded models silently with a 10 minute TTL; no audio documented | Measure speed from the stream; adopt checks loaded instances before loading; explicit loading only; audio decided by spike S5 |
| A2A protocol | Version 1.0; extensions are declared in the Agent Card, activated by a header, carry data in metadata, and can add methods; `returnImmediately` and push config exist; finished tasks reject new messages | Push docs recommend HTTPS webhooks and SSRF checks | The SDK's URL screening is opt-in; our localhost webhook is accepted |
| `a2a-sdk` (Python) | Version 1.2.1: server with SQLite task and push-config stores that survive restarts, `returnImmediately`, localhost push with a notification token, `INPUT_REQUIRED` continuation with a data part, `CancelTask` | Pushes every state change; task stores are scoped by caller identity; a task running at a crash stays `WORKING` (the SDK does not resume it); custom JSON-RPC methods are not pluggable | Filter pushes to terminal and input states; one owner scope for the single-owner system; the main agent reconciles open tasks at startup; `PauseTask`/`ResumeTask` served by a thin wrapper in front of the SDK dispatcher |

## Compatibility and change

Supported: A2A 1.0, MCP 2026-07-28 and earlier as negotiated, LM Studio's current REST API, llama.cpp as downloaded by setup. Breaking changes to events use a new `schema_version`; to the extension a new URI; to REST a new prefix. Contracts are verified by consumer and provider contract tests in the contracts package. No real keys, tokens, or private endpoints appear in this page.
